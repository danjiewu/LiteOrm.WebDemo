# 第12篇：性能对比与总结

> ⏱ 阅读约 10 分钟

作为本系列的终章，本文汇总 LiteOrm 的完整性能基准测试数据、与主流 .NET ORM 的多维度对比，以及使用场景建议。

## 测试环境

测试基于 [LiteOrm.Benchmark](https://github.com/danjiewu/LiteOrm) 项目：

| 项目 | 配置 |
|------|------|
| 运行时 | .NET 10.0.4 |
| 操作系统 | Ubuntu 24.04 LTS |
| CPU | Intel Xeon Silver 4314 @ 2.40GHz |
| 数据库 | MySQL 8.0 |
| 测试框架 | BenchmarkDotNet |

## 插入性能

| 框架 | 100条 | 1000条 | 5000条 |
|------|-------|--------|--------|
| **LiteOrm** | **3.98ms** | **16.39ms** | **75.62ms** |
| SqlSugar | 4.33ms | 19.12ms | 98.15ms |
| FreeSql | 4.36ms | 18.48ms | 85.00ms |
| EF Core | 18.50ms | 150.35ms | 670.19ms |
| Dapper | 26.19ms | 215.12ms | 1,129.57ms |

> **分析**：LiteOrm 在插入性能上全面领先。5000条批量插入比 EF Core 快近9倍，比 Dapper 快近15倍。原因是 LiteOrm 的 `BatchInsertAsync` 内部使用了高效的批量 SQL 构造，而 Dapper 虽然以性能著称，但在 Benchmark 中未使用批量优化。

## 更新性能

| 框架 | 100条 | 1000条 | 5000条 |
|------|-------|--------|--------|
| **LiteOrm** | **4.84ms** | **25.36ms** | **118.70ms** |
| FreeSql | 5.88ms | 40.31ms | 175.58ms |
| SqlSugar | 6.39ms | 42.62ms | 232.66ms |
| EF Core | 17.26ms | 126.44ms | 575.32ms |
| Dapper | 28.63ms | 248.71ms | 1,213.51ms |

> **分析**：更新性能同样是 LiteOrm 领跑。5000条批量更新比 EF Core 快约5倍。`BatchUpdateAsync` 的优势在大批量操作中愈发明显。

## Upsert 性能

| 框架 | 100条 | 1000条 | 5000条 |
|------|-------|--------|--------|
| **FreeSql** | **5.53ms** | **19.11ms** | **103.06ms** |
| LiteOrm | 7.54ms | 23.72ms | 103.52ms |
| SqlSugar | 10.36ms | 106.11ms | 1,741.49ms |
| EF Core | 19.05ms | 135.88ms | 589.07ms |
| Dapper | 29.09ms | 247.51ms | 1,248.91ms |

> **分析**：Upsert 是唯一 LiteOrm 略逊于 FreeSql 的场景，但差距极小（5000条仅差0.46ms）。相比 SqlSugar 在 5000条时的剧烈退化，LiteOrm 的表现更加稳定。

## 关联查询性能

| 框架 | 100条 | 1000条 | 5000条 |
|------|-------|--------|--------|
| **LiteOrm** | **1.36ms** | 9.35ms | 43.94ms |
| Dapper | 1.48ms | **9.07ms** | 45.64ms |
| FreeSql | 1.75ms | 9.10ms | **43.89ms** |
| EF Core | 4.93ms | 15.62ms | 55.16ms |
| SqlSugar | 2.29ms | 22.10ms | 89.97ms |

> **分析**：关联查询中 LiteOrm、Dapper、FreeSql 三者性能接近，差距在毫秒级。这是因为关联查询的主要开销在数据库端，ORM 层的差异被缩小。LiteOrm 的自动 JOIN 机制没有带来额外开销。

## 内存分配对比（1000条数据，KB）

内存分配是衡量 ORM 效率的重要指标，直接影响 GC 压力和可扩展性：

| 框架 | 插入 | 更新 | Upsert | 关联查询 |
|------|------|------|--------|----------|
| **LiteOrm** | **862.82** | **1,189.03** | **1,973.38** | **230.38** |
| FreeSql | 4,667.20 | 6,917.50 | 2,256.36 | 866.52 |
| Dapper | 2,476.36 | 3,093.19 | 2,798.36 | 418.43 |
| SqlSugar | 4,573.59 | 7,679.63 | 35,952.88 | 9,228.26 |
| EF Core | 12,503.04 | 9,044.24 | 9,005.39 | 2,198.05 |

> **关键发现**：
> - LiteOrm 插入 1000 条仅分配 **863KB**，而 EF Core 分配了 **12,503KB**——是 LiteOrm 的 **14.5 倍**
> - SqlSugar 在 Upsert 场景下内存暴增至 35,953KB，是 LiteOrm 的 **18 倍**
> - 关联查询中 LiteOrm 仅分配 **230KB**，是所有框架中最少的

内存效率直接关系到高并发场景下的系统吞吐量——LiteOrm 在这方面的优势非常显著。

## 各 ORM 适用场景

### LiteOrm
- **适合**：性能敏感的 Web 应用、需要动态查询+前后端集成的项目、需要分表的中大型系统
- **不适合**：对 Entity Framework 生态有深度依赖的项目（如大量使用第三方 EF 扩展）

### EF Core
- **适合**：功能优先、团队熟悉 EF 生态、与 ASP.NET Core Identity 等官方组件集成
- **不适合**：高性能要求的批量操作场景

### Dapper
- **适合**：极致性能需求、团队 SQL 能力强、简单项目
- **不适合**：复杂业务逻辑、需要 ORM 抽象的项目

### SqlSugar
- **适合**：国产项目、需要中文文档和社区支持
- **不适合**：对内存分配有严格要求的场景

### FreeSql
- **适合**：功能全面的需求、多数据库支持
- **不适合**：希望保持轻量依赖的项目

## LiteOrm 的独特优势总结

1. **性能与内存双优**：速度接近 Dapper，内存分配是所有 ORM 中最少的
2. **Expr 表达式系统**：Lambda + Expr + ExprString 三种查询方式可混合，动态查询构建无与伦比
3. **前后端一体化**：Expr JSON 序列化协议 + 安全验证器，形成安全的前后端查询链路；泛型 Controller 通过 WebDemo 提供参考示例
4. **声明式开发**：`[Table]`、`[Column]`、`[ForeignType]`、`[Transaction]`、`[ServiceLog]` 等特性，大幅减少样板代码
5. **原生分表**：`IArged` 接口一行代码实现动态分表路由，无需手写表名拼接
6. **安全内置**：参数化 + LIKE 转义 + ExprValidator + 函数策略，多层 SQL 注入防护
7. **扩展灵活**：表达式扩展、自定义 SqlBuilder、BulkProvider 等机制，满足定制需求
